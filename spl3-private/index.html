01募集と参加者の管理を、Botに任せる

Discordでプラベの参加者を募ると、「ノ」「行きます」といった返信を見ながら、誰が参加するのかを手で数えることになります。途中で抜ける人や、後から入る人がいると、さらに追いにくくなります。そこで、募集の作成から参加者リストの更新までを行うBotを作りました。

/プラベを実行すると、Botが募集メッセージを投稿します。参加者が増減するたびに新しいメッセージは送らず、同じメッセージを書き換えて最新の状態を表示します。

UI SAMPLE / 表示イメージ🎮 プラベ募集

⏰ 21:00～
⏳ 締切 10/17(土) 20:30
👥 参加者 4/8
・メンバーA
・メンバーB
・メンバーC
・ゲストD（新規）

参加方法
ボタン、またはチャットで「ノ」「行く」などと発言
取り消し
「参加取消」ボタン / 発言 / /取消
🙋 参加する参加取消

実際の操作はDiscord上で行います。

参加方法は、募集ごとに3種類から選ぶ

  • ボタン「参加する」「参加取消」ボタンで登録。AIを使わないので、確実で料金もかからない。
  • メッセージチャットの発言をAIが判定して登録。普段どおりの返信で参加できる。
  • 両方ボタンと発言のどちらでも参加できる。

定員（2〜10人）、開始時間、タイトル、締切時刻も指定できます。募集した人は、自動で参加者に入ります。締切を過ぎると募集は自動で【終了】になり、ボタンも消えます（締切を指定しない場合は、作成から6時間で終了）。

02「行く」の書き方は、人それぞれ

参加の意思表示は「ノ」「いきたい」「まだ空いてたら俺も行こうかな」など、人によってさまざまです。決まった単語だけで判定すると取りこぼしが出ますし、逆に「行きたいけど今日は無理」を参加扱いにしてしまいます。そこで、発言の判定にGemini APIを使いました。

判定の例
「ノ」「いきたい」JOIN（参加）
「まだ空いてたら俺も行こうかな」JOIN（参加）
「ごめんやっぱ無理」LEAVE（取り消し）
「行きたいけど今日は無理」NONE（何もしない）
「あと何人？」NONE（質問）
「○○さん行くの？」NONE（他の人の話）

自由な文章ではなく、決まった形で答えさせる

Geminiには文章で答えさせず、JSON Schemaで形式を指定した構造化出力を使いました。受け取った値もそのまま信用せず、Python側でもう一度検証します。形式が違う、値が範囲外、タイムアウトした、といった場合はすべて「何もしない」として扱います。

{
  "action": "JOIN",      // JOIN / LEAVE / NONE
  "confidence": 0.95     // 0.0〜1.0
}

直前の会話も一緒に渡す

1つの発言だけでは判断できない場面もあります。

A：何時から？
B：21時
A：なら行く → JOIN

このような流れを読み取れるように、直前の発言を最大5件（10分以内）まで判定材料として渡しています。API料金とプライバシーを考え、それ以上の履歴は送りません。

名前は送らない

Geminiに送る会話では、発言者の名前やIDを「TARGET」「U1」のような仮の名前に置き換えています。ログにもメッセージ本文は残さず、記録するのは判定結果とIDだけです。

03AIが間違えても、人が直せる

AIの判定は必ずどこかで間違えます。そこで、「勝手に参加させない」ことと「間違えたらすぐ直せる」ことを優先して設計しました。

  • 迷ったら何もしない確信度が0.85未満の判定は反映しない。曖昧な発言、質問、雑談、他の人についての話は参加扱いにしない。
  • 判定結果を見せる参加として処理した発言に✅、取り消しには👋、満員のときは🈵のリアクションをBotが付ける。
  • 手で直せる参加取消ボタンや/取消で修正できる。募集者は、他の人の誤登録も取り消せる。

1つのチャンネルに、AI判定の募集は1件まで

同じチャンネルに募集が2つあると、「行く」がどちらへの返事なのか分かりません。スレッドを使って分ける方法も考えましたが、まずは仕組みをシンプルにするため、メッセージ方式の募集は1チャンネル1件までにしました。ボタン方式はボタンが募集ごとに分かれているので、いくつ作っても混ざりません。

同時に押されても壊れない

何人かが同時にボタンを押しても定員を超えないよう、募集ごとにロックをかけて処理しています。さらに、データベース（SQLite）の制約でも二重登録を防いでいます。20人が同時に参加しようとして、定員ちょうどで締まることを自動テストで確認しました。

04使ってもらって、足した機能

公開後も、実際に募集で使いながら気になった点を直し、機能を足していきました。追加したものをまとめます。

  • 名前で表示参加者を<@ID>のメンションで並べていたところ、見る人の環境によってはIDのまま表示されていた。Botがサーバー内の表示名を取得して、文字列として埋め込むように変更。Members Intentは使わず、取得した名前は数分間キャッシュしてAPI呼び出しを抑えている。
  • 締切を時刻で/プラベの「締切」に「22:30」のような日本時間の時刻を指定できるようにした。/締切で今すぐ締め切ったり、締切時刻を変えたりもできる。
  • /引き継ぎ誤って締め切った募集の参加者を、参加順のまま新しい募集へ移す。定員を超える分は追加せず、追加できなかった人を結果に表示する。
  • /追加募集者が参加者を手動で追加できる。サーバーにいない人（Xのフォロワーなど）も、名前だけのゲストとして登録でき、募集には「名前（新規）」と表示される。

締切は「人が書きそうな形」で受け付ける

締切の入力は自由入力にして、よく使う書き方をまとめて解釈するようにしました。全角の数字や記号も半角に揃えてから読み取ります。

締切の入力例
「22:30」「22時30分」「２２：３０」今日の22:30
「0:30」（今日はもう過ぎている）翌日の0:30
「10/18 22:30」10月18日の22:30
8日後の日時エラー（7日以内のみ）

締切を過ぎた参加操作はその場で受け付けず、募集メッセージは1分ごとの確認で【終了】に切り替わります。

動いているデータを壊さずに足す

締切とゲストのために、データベースへ列を2つ追加しました。SQLiteのuser_versionでスキーマのバージョンを管理し、Botの起動時に足りない分だけ自動で移行します。VPSではgit pullして再起動するだけで、募集中のデータもそのまま使えます。ゲストには負の数の内部IDを割り当て、DiscordのユーザーIDとは絶対に重ならないようにしました。自動テストも55件から101件に増やしています。

05メモリ1GBのVPSで、常時稼働させる

開発はWindowsで行い、GitHubを経由して、ConoHa VPSのUbuntuで動かしています。VPSのメモリは1GBしかないため、Dockerは使わず、Pythonを直接systemdで動かす構成にしました。

メモリを節約するため、Discordのメッセージやメンバー情報をBot側に溜め込まない設定にしています。AIの判定に使う直前の会話も、募集中のチャンネルごとに5件だけ保持します。

  1. GitHubからclone

    VPS上でvenvを作り、バージョンを固定した依存パッケージをインストール。

  2. 秘密情報はGitの外に置く

    DiscordのトークンとGemini APIのキーは、権限を絞った設定ファイルに保存し、systemdから読み込む。

  3. 専用ユーザーで実行

    rootでは動かさない。Botが書き込めるのはデータベースのフォルダだけに制限。

  4. systemdで自動起動・再起動

    VPSの起動時に自動で立ち上がり、異常終了しても再起動する。メモリ使用量にも上限を設定。

systemctl status splatoon-recruit-bot
journalctl -u splatoon-recruit-bot -f
VPS上で active (running) を確認

Discord上で募集の作成、ボタンでの参加、発言からのAI判定が動くことを確認しました。更新は、GitHubにpushしてVPSでgit pullし、サービスを再起動するだけです。

開発中につまずいたこと

コマンド登録で「Missing Access」

ログインは成功したのに、スラッシュコマンドの登録で403エラーになりました。指定したサーバーIDとBotの招待設定を見直して解決しました。原因が分かりやすいよう、このエラーのときは確認すべき点をログに出すようにしています。

Message Content Intentが無効

発言の内容を読むには、Discord Developer Portalで特別な権限（Intent）を有効にする必要がありました。ボタン方式だけで使う場合はこの権限を要求しないようにして、必要な権限を最小限にしています。

公開リポジトリにメールアドレス

コミットに個人のメールアドレスが記録されていました。GitHubの非公開用アドレスに書き換えて、履歴を置き換えました。
